# Upgrade an existing kei backup

These steps apply to v0.30 (schema 48). If you are installing v0.26.0, use the [guide at the v0.26.0 tag](https://github.com/rhoopr/kei/blob/v0.26.0/docs/v0.26.0-upgrade.md). For another older release, read the documentation at its tag.

1. Before opening state, even with `kei status`, stop every writer, including watch processes, services and containers. Back up the configuration, entire data directory (including SQLite journal, WAL and SHM files), and media tree (including sidecars and hidden history) together. Verify the copy and retain the previous binary or image. To roll back, stop every writer and restore that matched set before starting the older binary.
2. Work on a copy of your config. Follow the [rendition-policy migration](rendition-policy-migration.md) before adding `config_version = 1`. Review the edits, RAW/JPEG renditions and Live Photo components that your first sync can download. If you previously used `edited_naming = "primary"`, see [edited filenames and existing layouts](edited-primary.md).
3. Check service arguments as well as TOML. Remove `--recent`, `--recent-scope`, `[filters].recent` and `[filters].recent_scope` from sync and service configurations. If you want a sample, set inclusive `skip_created_before` and `skip_created_after` dates such as `2025-01-01` and `2025-01-07`; choose dates from your own library. Removing a count limit without replacing it can select much more media. `import-existing --recent N` still samples by count.
4. If your database predates account-bound state (v0.24.x or earlier), follow [account-state adoption](account-state-migration.md) before running sync. Verify ownership independently and sign in with the same account and region. Do not rename old credentials or confirm a database of uncertain ownership.
5. Review `kei config show --config /path/to/config.toml`, then run `kei sync --config /path/to/config.toml --dry-run`. Check the selected libraries, albums, date range and destination before running the same sync without `--dry-run`. Keep the cold backup: a preview is not a substitute for it.
6. Run `kei status` against the same configuration and open a few downloaded files. Run ordinary `kei sync` again for unfinished work. If one existing file looks damaged, follow [Backup maintenance](backup-maintenance.md) to inspect that copy before authorizing replacement. A successful sync does not verify every historical file.

Every schema upgrade needs room for a temporary copy of the database and configuration beside the live database. After committing the upgrade, kei reopens the database and checks the account, schema version, SQLite integrity and foreign keys. Once those checks pass, it deletes that upgrade's temporary bundle. If migration or verification fails, keep the bundle and follow its `restore.txt`. Older backups stay untouched. Keep your own backup from step 1 if you want to roll back after a successful upgrade.

Schema 45 retires the old v0.26 provider responses. On RC and beta upgrades it removes the three old inbox archive tables from the live database. After releasing the temporary backup, kei compacts the live file if at least 8 MiB can be reclaimed and logs its size before and after. If another connection is using the database or disk space is too low, sync can proceed and the next writable open retries.

Schema 46 lets a normal sync release enumeration responses for completed selections. An interrupted baseline keeps its evidence and can grow past the old 512 MiB limit. Resume with `kei sync` using the same state. SQLite can reuse space released by completed selections even if the database file stays the same size.

Schema 47 records the output of a successful metadata writer, including the XMP packet when sidecars are enabled. Existing rows start without this proof. Normal sync builds it as it drains pending metadata.

Schema 48 indexes membership pages and destination identities so a sync can look up one asset without scanning unrelated records. The migration marks historical membership pages from their retained records. Every rank page and record stays in place.
